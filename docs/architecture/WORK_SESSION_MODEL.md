# Work Session Model

## Purpose

This document defines the lifecycle of a work session.

A work session is not simply a timed interval.

It is an intentional cycle of planning, execution, reflection, and learning.

Every work session should leave the system with more knowledge than it had before.

---

# Philosophy

A work session is an experiment.

The user begins with an intention.

Reality determines the outcome.

The application should preserve both the original intention and the actual outcome.

---

# Session Lifecycle

Every work session progresses through the following stages.

1. Preparation
2. Planning
3. Execution
4. Reflection
5. Outcome
6. Context Update
7. Transition

The session is considered complete only after its outcome has been captured.

---

# Session Intention

Before work begins, the user records the intended outcome.

Examples:

* Design AI architecture
* Review pull request
* Fix login bug
* Investigate performance issue

Optional planning information:

* expected duration
* expected deliverables
* repository
* branch
* related project
* success criteria
* assumptions

This establishes the baseline against which the session may later be evaluated.

---

# Session Outcome

Every work session must end with exactly one outcome.

Possible outcomes include:

* Completed
* Partially Completed
* Blocked
* Replanned
* Superseded
* Cancelled
* Interrupted
* Research Completed
* Decision Reached

All outcomes are considered valid.

The objective is to preserve learning, not to maximize completion rates.

---

# Outcome Reflection

Every session should answer four questions.

1. What happened?
2. Why did it happen?
3. What changed?
4. What should happen next?

These answers become part of the project's knowledge.

---

# Learning Capture

Every session should contribute one or more of the following:

* new knowledge
* decisions
* assumptions
* blockers
* risks
* open questions
* future actions

A session that changes understanding is successful, even if implementation did not occur.

---

# Context Update

After reflection, the application's knowledge should be updated.

Examples:

* project context
* context snapshot
* decisions
* blockers
* next action
* resume brief

The next work session should benefit from everything learned.

---

# Repository Evaluation (Future Capability)

If linked to a local Git repository, the application may compare:

* intended outcome
* repository evidence
* implementation progress
* test status
* code quality indicators

The purpose is to assist reflection, not to score the user.

Repository evidence is one input into the session outcome—not the outcome itself.

---

# Session Success

Success is determined by improved understanding.

Examples of successful sessions include:

* discovering that a feature should not be built
* identifying a hidden dependency
* reducing project risk
* making a significant architectural decision
* validating or rejecting an assumption

Completion is one possible success, not the only one.

---

# Design Principles

The work session model should:

* encourage honest reflection
* reduce planning anxiety
* reward learning
* preserve context
* support changing priorities
* improve future planning accuracy
* strengthen long-term knowledge

---

# Future Opportunities

Potential future capabilities include:

* AI-assisted session planning
* AI-generated wrap-up drafts
* repository-aware evaluation
* planning accuracy metrics
* recurring blocker detection
* adaptive session duration
* personalized planning recommendations

These capabilities should reinforce the core principle that every session is an opportunity to improve the user's understanding of their work.
